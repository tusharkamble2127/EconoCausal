## Authentication

All run data, dataset, and campaign endpoints require a valid JWT bearer
token obtained from `POST /auth/login`. Tokens are passed in the
`Authorization: Bearer <token>` header.

- **Register** (`POST /auth/register`): creates a user and returns an
  `access_token`. Passwords are hashed with **PBKDF2-HMAC-SHA256 at 260,000
  iterations** (stdlib `hashlib`, no extra dependency).
- **Login** (`POST /auth/login`): validates credentials and returns a bearer
  token. Invalid credentials return `"Incorrect email or password."` (no
  distinction between a bad email and a bad password).
- **JWT config:** `HS256` algorithm, `ECONOCAUSAL_JWT_SECRET` key,
  `ECONOCAUSAL_JWT_EXPIRE_MINUTES` lifetime (default 480 = 8 hours).
- **Frontend storage:** the token is stored in `localStorage` under key
  `econocausal_token`; `useAppContext` exposes `isAuthenticated`, `login`,
  and `logout`.
- **Auth guards:** `ProtectedRoute` in `frontend/src/App.jsx` redirects
  unauthenticated users to `/login`. Every protected API endpoint independently
  enforces authentication via `get_current_user` in `app/api/deps.py`.

- Authenticated users who do not own a run or dataset receive HTTP 404
  (not 403) to avoid leaking resource existence.
- Anonymous callers receive HTTP 401 on all protected endpoints.
- Only `GET /health` remains unauthenticated (liveness probe by design).

## Password Reset

| Method | Path | Purpose | Auth |
|--------|------|---------|------|
| POST | `/auth/forgot-password` | Initiate a password reset. Always returns the same generic message whether or not the email exists (account-enumeration protection). | No |
| POST | `/auth/reset-password` | Complete a password reset with a valid token. Accepts `{ token, new_password }`. | No |

### Security properties

| Property | Implementation |
|----------|----------------|
| Token generation | `secrets.token_urlsafe(32)` (32 bytes, URL-safe) |
| Token storage | SHA-256 hash only (`hash_reset_token`); raw token never stored |
| Token expiration | `ECONOCAUSAL_PASSWORD_RESET_EXPIRE_MINUTES` (default 30 minutes) |
| One-time use | Token is rejected if `used_at` is set; `mark_used` stamps `used_at` after a successful reset |
| Rate limiting | 60-second cooldown between reset requests (`RESET_COOLDOWN_SECONDS = 60`); HTTP 429 on violation |
| Account enumeration protection | Identical generic 200 response for existing and non-existing emails |
| Old-password rejection | After a reset, the previous password no longer authenticates (401) |
| Invalid token | HTTP 400 ("invalid or expired") |
| Weak password | Passwords shorter than 6 characters return HTTP 422 |
| Token/URL never logged | The raw token and reset URL are never written to logs |

### Email delivery

Password reset emails are sent through **Brevo** (preferred, when
`ECONOCAUSAL_BREVO_API_KEY` and `ECONOCAUSAL_BREVO_TEMPLATE_ID` are set) or
**SMTP** (fallback, driven by `ECONOCAUSAL_SMTP_*`). The backend POSTs to
Brevo's transactional endpoint (`https://api.brevo.com/v3/smtp/email`) with
the reset URL passed as `params.reset_url`.

**Verified state (2026-08-27):** Brevo API credentials are loaded from
`.env` and the request format is correct (POST to
`https://api.brevo.com/v3/smtp/email` with the proper `api-key` header and
`params.reset_url` payload). However, Brevo returns **HTTP 401 Unauthorized**
("unrecognised IP address") because the server's egress IP is not registered
in the Brevo dashboard under **Settings → Authorized IPs**. This is an
**environment configuration issue**, not an application bug. The application
handles this gracefully: the `EmailError` raised by the email service is caught
in `password_reset_service.forgot_password` and the generic enumeration-safe
response is still returned; the reset token is generated and persisted
regardless of email delivery. Actual inbox delivery is **not verified**.

## Run Lifecycle

The backend runs the full causal pipeline **synchronously** within the
`POST /runs` request:

1. `pending` (model default)
2. `running` (set when a run is created via `POST /runs`)
3. `complete` or `failed` (set when the synchronous pipeline finishes)

The frontend (`useRun` hook in `frontend/src/hooks/useRun.js`) polls
`GET /runs/{run_id}` every 1.5 seconds until `status` is `complete` or
`failed`. The Axios client timeout of **600 seconds**
(`frontend/src/api/client.js`) accommodates the synchronous pipeline on large
datasets (2,000+ rows can take 15–60 seconds).

## Error Envelope

```json
{
  "error": "<ExceptionClassName>",
  "detail": "<human-readable explanation>"
}
```

Every custom exception in `app/core/exceptions.py` maps to one of 400, 404,
409, or 422 via the single handler registered in `app/main.py`. The global
exception handler returns this generic envelope instead of raw stack traces.

## Confidence Score

The `confidence_score` field returned by `/runs/{run_id}/recommendations`
and `/runs/{run_id}/customers/{customer_id}/explanation` is a **reliability
index** in the range `[0, 1]`. It is **not** a probability that the
recommendation is correct.

The score is a deterministic composite of five statistically grounded
components:

| Component | Weight | Description |
|-----------|--------|-------------|
| Statistical precision | 0.30 | Narrower estimator confidence interval => higher score. The outcome scale is purchase probability, bounded on [0, 1], so absolute CI width is an appropriate precision signal. |
| Signal-to-noise ratio | 0.25 | Point estimate magnitude relative to CI width. |
| Refutation robustness | 0.15 | DoWhy refutation test pass rate. When refutation is unavailable, a conservative heuristic fallback of 0.75 is used; this does NOT imply successful refutation. |
| Sample adequacy | 0.10 | Minimum sample size for usable estimates. The n >= 30 threshold is a heuristic rule-of-thumb, not a universal statistical guarantee. |
| Data support | 0.20 | Propensity overlap, common support, and matching coverage. Four distinct diagnostics are retained: percent outside common support, percent with extreme propensity scores, number of unmatched treated units, and complete matching collapse (zero pairs with unmatched treated). |

**Confidence levels:**
- `High`: CI excludes zero, strong precision, refutation passed, adequate sample, adequate treatment variation, and adequate data support.
- `Moderate`: CI excludes zero, reasonable precision, refutation passed, and adequate data support.
- `Low`: Valid finite CI with adequate data support.
- `Insufficient Evidence`: Missing/invalid CI, zero discount, tiny sample, insufficient treatment variation, or poor data support.

When uncertainty cannot be estimated (e.g., missing CI, NaN/Inf bounds,
reversed bounds, or poor propensity overlap), the API returns
`confidence_score: 0.0` and `confidence_level: "Insufficient Evidence"`.
